Research done to inform the cap/price decision (2026-09-05, user-requested, high effort):
- **Average usage**: most AI-assistant users are not daily power users (only 41% of ChatGPT's MAU use it 3+×/week). The closest real comparable to this app's cost profile, Perplexity's "Deep Research" mode, caps even paying $20/mo subscribers at only **~20/month**.
- **Worst-case/power-user %**: no AI-specific published number exists (Perplexity didn't disclose one when they cut their own limits), but the general SaaS/freemium pattern is a Pareto split -- **roughly the top 20% of users drive the large majority of usage**. Design assumption: ~1-in-5 subscribers will be a genuine heavy user regularly approaching the cap; the rest use a fraction of it.
- **Iraqi market pricing (direct comparable found)**: resold/shared ChatGPT Plus seats are actively sold on Iraqi Instagram right now for **7,000 IQD/month** -- same product category, same social-media-resale channel the user described from personal experience. Combined with Telegram Premium (~$5 ≈ 6,550 IQD) and the earlier Spotify anchor (4,900 IQD), the accepted range for a paid digital subscription in Iraq clusters around **5,000-7,000 IQD/month**. Official ChatGPT Plus ($20 ≈ 26,000 IQD) is far outside what the local market actually pays directly.
- **Cap options costed out and the final decision**: 100 (old flat cap) = 23,000 IQD worst-case, badly underwater vs. a 6-7k price; **40/30/20 (chosen) = 9,200 / ~8,910 / 6,400 IQD worst-case vs. 6,000 / 7,000 / 8,500 IQD prices -- normal and pro can lose money at full use (accepted risk), max stays profitable even then**; 25/20/15 (the more conservative option originally recommended) would have kept every tier profitable even at full use but was passed over for a more generous/appealing number.

## Known open issues (not on the original roadmap, found during testing)

- [x] Intermittent `PipelineError` on some questions — root-caused via Sentry: OpenAlex transient failures (429/5xx/timeout) had no retry and the real per-query errors were discarded from the exception message. Fixed in `openalex_search.fetch_results()` (one retry) and `pipeline_runner.py` (error message now surfaces the real cause). See commit `19b0ff8`.
- [ ] Streamlit Cloud sometimes serves a stale/partially-reloaded module after a push (hit three times now: `FIREBASE_KEY`, `auth.is_subscribed`, `run_assistant.make_relevance_classifier`) — fix is always a full Reboot from the app's ⋮ menu, not just a save/refresh. Consider whether this is worth a standing habit: always Reboot after every push, not just when something breaks.
- [x] Moderation wrongly rejecting a normal follow-up question — found live: "give me more information and sources" (a completely normal way to continue an existing research thread) was rejected as "not a specific research question." Same root cause and same fix pattern as the earlier paper-caption bug: the general moderation prompt judges text as a *freestanding* question, an unfair bar for a follow-up that only makes sense in context of an existing thread. Fixed with `moderation.format_followup_moderation_prompt()`, wired into `handle_followup_input()`. See commit `e504843`. **Second time this exact bug class has appeared (paper captions, now follow-ups) -- worth remembering: any place a short/contextual user input is checked by moderation needs a context-aware prompt, not the generic freestanding-question one.**
- [x] `PipelineError` at the extraction stage after the full-length-output change — the prompt (`pipeline_runner.py`) was raised to allow up to 3 disagreements / 4 limitations, but `synthesis.py`'s validator caps were left at the old 2/3, so a correct, real model response hit "exceeding the maximum" and failed. Fixed by syncing the validator constants to the prompt's stated limits. See commit `f8537c9`. **General lesson: whenever a prompt's stated limit changes, the matching validator constant must change with it in the same edit** -- these two files drifting apart is exactly this bug's root cause, and it's an easy mistake to repeat.
- [x] `PipelineError` at relevance classification: "Item 2: unexpected field(s) not allowed: ['title']" — found live right after the fix above, on retry. Root cause: relevance classification was the one AI-boundary stage still using plain-text "please return exactly these fields" prompting instead of Anthropic's native JSON Schema structured output (which moderation/extraction/synthesis already used) -- so nothing structurally stopped the model from occasionally adding an extra field, which the validator then correctly rejected. Fixed by migrating it to the same native-schema pattern (`relevance_filter.RELEVANCE_JSON_SCHEMA`, `additionalProperties: false`). See commit `b889c6a`.
- [x] Token-usage box always showed whatever action ran last, attached to the wrong part of the page — e.g. a follow-up's cost appeared to belong to the original result. Root cause: the expander read the shared global `backend.TOKEN_USAGE_LOG` directly instead of a snapshot. Fixed 2026-09-05 by having each action (search/expand/follow-up) snapshot its own usage right after its model call(s) complete and store it on its own entry; new `render_token_usage()` helper displays whichever snapshot belongs to what's actually being shown. See commit `31a9a53`.
- [x] Sidebar collapse toggle jumping around / leaving blank space — user noticed the toggle moves left/right and leaves empty space when collapsed. Root-caused by inspecting the live app directly in the browser (found the actual computed transform, not guessed): Streamlit collapses the sidebar via a hardcoded `transform: translateX(-300px)`, built assuming a left-side LTR sidebar. This app's RTL layout puts the sidebar on the right, so collapsing slid it into the main content instead of off-screen. Fixed with a rule targeting `section[data-testid="stSidebar"][aria-expanded="false"]` to translate the opposite direction; confirmed live (both collapse and reopen) before committing. See commit `9e0340d`. Likely also the cause of the "not phone-friendly" look reported on mobile, since mobile starts with the sidebar collapsed by default -- not yet separately confirmed on a real phone after this fix.
- [x] Sidebar still took up most of a phone screen even after the collapse fix above — separate bug: the sidebar's forced width was a flat `300px` regardless of screen size, so on a ~375px-wide phone it ate ~80% of the screen whenever open. Fixed to `min(300px, 85vw)` (stays exactly 300px on desktop/tablet, caps to 85% of whatever width is actually available on a narrow phone); the collapse-transform rule uses the same expression so it still slides exactly the sidebar's current width off-screen at any size. See commit `f0772b3`. **Not yet confirmed on a real phone** (browser-based live verification was attempted but the preview pane went hidden mid-test).
